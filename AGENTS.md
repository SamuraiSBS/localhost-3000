# localhost-3000

- До появления ТЗ готовим инфраструктуру и утверждённую независимую дизайн-систему. Не придумываем продуктовые сценарии. `infra/probe` — заменяемый стенд, не выбранный стек продукта.
- После получения ТЗ сначала заполнить `docs/challenge.md`, `rules.md`, `evaluation.md`; проверить допустимость заранее подготовленного кода. Затем выбрать простой стек под критерии и определить работающий MVP.
- Сначала основной пользовательский сценарий и критерии жюри, затем дополнительные возможности. Новые сервисы и зависимости должны решать конкретную задачу.
- Перед изменениями проверить `git status`, прочитать относящиеся документы; сохранять чужие изменения. Не удалять файлы без понятной причины, не использовать destructive reset/clean.
- Исправлять обнаруженные ошибки в рамках задачи. После существенных изменений запускать подходящие тесты; перед коммитом `python scripts/check.py` и `git diff --check`. Сохранять проект запускаемым.
- Использовать короткие ветки `feat/*`, `fix/*`, `infra/*`, `docs/*`, небольшие осмысленные коммиты и PR с описанием результата и проверок. Основная ветка — `main`.
- Секреты только в локальном `.env`, SSH-agent или GitHub Secrets. `.env.example` содержит безопасные значения. Не выводить токены, приватные ключи и полные окружения.
- Документировать существенные решения в `docs/decisions.md`, состояние инфраструктуры — в `docs/infrastructure.md`; поддерживать инструкции запуска при изменениях.
- Для браузерных сценариев использовать доступный browser tool; API-проверки не заменяют E2E. Перед защитой пройти `docs/demo.md` и ключевой сценарий на узком и широком экранах.
- Отличать подготовленную конфигурацию от выполненной проверки. CI, Docker, VPS, HTTPS и публичный E2E отмечать отдельно, с фактическими доказательствами.
- Не покупать ресурсы, не менять видимость репозитория, DNS и защиту доступа без соответствующего контекста и полномочий. Не отключать защиту ради прохождения проверки.

Локальные навыки находятся в `.agents/skills/`: `hackathon-planner`, `mvp-builder`, `devops-deploy`, `demo-qa`. Использовать по назначению; они дополняют эти правила проектными процедурами.

## Автономная команда «Выполняй план MVP»

- Прямое поручение пользователя `Выполняй план MVP` запускает процедуру из `docs/EXECUTE_PLAN.md`. Обсуждение, цитирование и настройка этой команды сами по себе не запускают продуктовые работы.
- Текущий чат становится оркестратором. На каждую задачу он создаёт отдельного worker через доступные инструменты субагентов, а на каждый цикл review — нового независимого reviewer. Не создавать пользовательские чаты для внутренних ролей.
- Перед правками резервировать точную задачу, файлы и runtime resources через `scripts/mvp_coordination.py`; состояние — `.agent-state/mvp-coordination/claims.json`. Привязать настоящий ID worker, затем Check/Claim. Резерв без Claim не разрешает редактирование. Не менять реестр вручную.
- Worker реализует только свой scope; reviewer проверяет точную версию read-only. После NO-GO тот же worker исправляет тот же claim; следующий reviewer новый. Только оркестратор принимает текущий GO с совпадающим manifest. Файлы/ресурсы заняты также во время review и при blocker, автоматического expiry нет.
- Источник текущего исполнения — реестр, `docs/backlog.json` задаёт план и зависимости. Не ставить done по одному отчёту worker. После принятого среза заново проверять готовность и продолжать P0 до B11; дополнительные P1 не входят в эту короткую команду без расширения задания.
- Повторная команда продолжает проверенное состояние и не дублирует занятые задачи. Нехватку обычных локальных зависимостей/сервиса/браузерной сессии устранять в task-owned scope; реальные неизвестные правила/внешние предпосылки фиксировать с источником и проверять другие независимые задачи.
- Команда охватывает локальную реализацию, тесты, browser QA, подготовку сдачи и небольшие проверенные локальные commits в отдельной короткой ветке. Перед первым продуктовым Claim сохранить просмотренные планы/координатор отдельным checkpoint; чужие dirty/staged файлы не включать. Короткая команда не разрешает push, публичный deploy, сообщения третьим лицам, покупки, изменение DNS/доступов или публикацию исходных материалов.

## Дизайн: Digital Ruins / Lost Signal

- Перед любой работой с интерфейсом прочитать `docs/design/README.md`, `DESIGN_SYSTEM.md`, `VISUAL_IDENTITY.md` и относящиеся правила компонентов/эффектов в той же папке. После получения ТЗ сначала изучить их, затем проектировать функциональность.
- Визуальный язык утверждён пользователем: цифровые руины, холодная уединённость, монохром, мелкоточечный дизеринг; 80% ретро / 20% современность. Не заменять его типовым SaaS, AI dashboard или маркетинговым шаблоном без явного решения пользователя.
- Единственный исполняемый источник токенов — `design/tokens.css`; использовать основу `design/foundation.css`, не копировать значения в новые темы. Палитра почти чёрная, без синей подложки; спектр — редкое оптическое явление, ориентир до 5% видимой площади.
- По последнему уточнению пользователя единый шрифт — локальный PP Neue Machina Inktrap для всего текста, заголовков, меню, контролов и wordmark. Он заменяет прежний JetBrains Mono. Утверждён вариант Б: главный заголовок 32 px, заголовок блока 24 px, обычный текст 16 px при стандартной базе; веса 500/400, wordmark 600. Сохранять масштабирование и читаемую кириллицу.
- Запрещены мелкие декоративные подписи, псевдостатусы, случайные индексы, координаты, номера секций и английские системные фразы ради атмосферы. Полезные подписи и обычный текст — от 16 CSS px, с достаточным контрастом.
- Сохранять художественную главную сцену: три разные повреждённые колонны по центру, ниже читаемый lowercase wordmark `localhost3000`, затем `ENTER SYSTEM`, вокруг много пустоты. Готовые ассеты находятся в `design/assets`, их происхождение и хеши сохранены рядом. Не подменять их случайными SVG-заглушками.
- Для будущей рабочей области использовать верхнюю плоскую Terminal Bar; пункты определяет ТЗ. Выбран Aceternity Liquid Glass с пресетом Controls из `--liquid-glass-*` в токенах; материал только для оправданных плавающих элементов. Старый Prism — отдельный ранний прототип. Blur сам по себе не является преломлением.
- Перед новым эффектом проверить доступные skills/MCP/библиотеки и `docs/design/IMPLEMENTATION_GUIDE.md`. Не добавлять тяжёлые зависимости для статичной графики. Рецепты и fallback — в `docs/design/EFFECTS.md`.
- Проверять адаптивность, клавиатуру, видимый фокус, масштабирование и reduced motion по `docs/design/DESIGN_QA_CHECKLIST.md`. Подготовленный токен/рецепт не означает проверенный эффект.
- ТЗ определяет функциональность, дизайн-система — визуальную идентичность. Исключения адаптировать минимально, сохраняя доступность; существенные решения фиксировать в `docs/decisions.md`. До ТЗ дизайн проверяется изолированно, не заменяет probe и не выбирает стек продукта.
