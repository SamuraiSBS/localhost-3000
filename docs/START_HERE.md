# Начать здесь: анализатор рисков оттока

Подготовлено 23 октября 2026 года по 14-страничному ТЗ и файлам `материалы/data`. **Пакет планирования готов; конкурсный продукт пока не реализован.** Исходные материалы сохранены. Текущий запускаемый сервер — инфраструктурный probe, страницы `design/` — отдельные образцы.

Для автономной реализации предусмотрена команда **«Выполняй план MVP»**: [запуск и роли](EXECUTE_PLAN.md). Она использует оркестратора, настоящих worker/reviewer и локальный реестр бронирования по образцу MTCH; настройка команды сама по себе не запускает продукт.

## Что нужно построить

Панель помогает маркетологу ответить: **кому требуется внимание, почему есть риск и сколько стоит возможное непродление**.

1. Вход по логину/паролю с защитой панели и клиентского API.
2. Клиентские score, высокий/средний/низкий риск, конкретные причины; при нехватке данных — явное отсутствие оценки.
3. Рейтинг с ID, email, балансом, общими пополнениями и score; сортировки ID/email/balance/totalReplenished в обе стороны и фильтрация.
4. Настройки коэффициентов через UI, реальное влияние на расчёт и сохранение после restart.
5. Объяснимая денежная сумма, учитывающая услуги, доступные средства и риск.
6. Автообновление списка, score и денег при новых данных/настройках без reload.
7. Точные REST endpoints, актуальный Prometheus `/metrics`, Swagger `/api/v1/docs` и приложенный OpenAPI-файл.
8. Расширяемые признаки, запуск Compose, исходники и понятная инструкция.
9. Защита: найти клиента → объяснить риск/деньги → изменить коэффициент/данные → увидеть обновление.

OIDC и график оттока дают дополнительную оценку. Они не заменяют обязательные условия. Баллы/веса критериев в PDF не опубликованы.

## Рекомендованный MVP

**FastAPI + Pydantic + Uvicorn + sqlite3 + pwdlib/Argon2 + prometheus-client**, один процесс/volume, native HTML/CSS/ES modules поверх текущих tokens/foundation. Готовые библиотеки закрывают HTTP, валидацию, password hashing, документацию, хранение и метрики. Предметная работа — небольшая прозрачная модель, объяснения и связный UI. Точные версии фиксируются проверенным build; пакеты в рамках анализа не устанавливались.

Четыре экрана: вход, рейтинг, карточка клиента, настройки/источник. Четыре признака v1: близость продления, отключённое автопродление, нехватка общей корзины, ожидание оплаты. Score по услуге → максимум клиента; деньги — стоимость одного ближайшего продления каждой услуги, взвешенная её score. Подробности и ручные эталоны в [model.md](model.md).

Почему без обучения: всего10 аккаунтов/30 услуг/100 транзакций, нет churn labels и истории статусов. Балансы не согласованы с полной платёжной историей; все текущие prolong_wait старше5 дней; нехватки средств для одного следующего продления в исходном fixture нет. Для наглядности нужны **отдельные помеченные расширения**, не изменение оригинала. Риск-индекс не объявляется статистической вероятностью, исторический ряд не выдумывается.

## Порядок реализации

Сначала B00 — уточнить OSS/prebuilt/AI; дедлайн/канал и права распространения выяснять параллельно, закрыть перед соответствующей сдачей/публикацией. Затем B01–B05 — данные → pure engine → persistence/auth → API. B06–B07 — полный браузерный путь и live update. B08–B11 — metrics/docs/Compose/приёмка/передача. Только после зелёного P0 — один P1 бонус с запасом на повторную QA и обновление пакета.

Пошаговые критерии готовности: **[implementation-plan.md](implementation-plan.md)**. Для нового Codex запуска: **[agent-workflow.md](agent-workflow.md)** и **[backlog.json](backlog.json)**. У всех продуктовых задач сейчас planned/needs_external_answer, доказательств выполнения ещё нет.

## Вопросы, влияющие на старт и сдачу

В PDF не определены разрешения на заготовки/OSS/AI, точный cutoff/канал сдачи и права публикации данных. Они перечислены как Q-001–005; молчание документа не является ответом. Выбор языка/фреймворка и формулы прямо оставлен команде. Для `/metrics` планируется аутентифицированный сборщик, для Swagger — сессия (Q-007). Шрифт PP Neue Machina proprietary; локальная пробная подготовка не подтверждает права публичного распространения.

Публичный сайт подтверждает формат23–25 октября и48 часов, но точный дедлайн кейса неизвестен. Планы относительные, на финальные20–25% оставшегося времени выделен резерв приёмки/сдачи. Источники и дата проверки находятся в [rules.md](rules.md).

Внешних действий по этим вопросам не выполнялось: никому не отправлены сообщения, репозиторий/данные не опубликованы, платные ресурсы/доступ/DNS/CD не менялись. Это законченная подготовка к следующему поручению на реализацию.
