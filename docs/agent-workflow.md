# Как передать реализацию Codex

Команда **«Выполняй план MVP»** закреплена в корневом AGENTS.md. Её процедура — [EXECUTE_PLAN.md](EXECUTE_PLAN.md), инструкции трёх ролей и бронирования — `docs/coordination/`. Настройка команды не запускает продукт и не разрешает отсутствующие конкурсные условия. При её прямом запуске оркестратор ведёт P0 через последовательные проверенные срезы.

## Порядок чтения

1. Корневой [AGENTS.md](../AGENTS.md), [EXECUTE_PLAN](EXECUTE_PLAN.md), [START_HERE](START_HERE.md), статус CLI; неизвестные условия — [rules](rules.md), [open-questions](open-questions.md).
2. [challenge](challenge.md), [requirements](requirements.md), [evaluation](evaluation.md).
3. [data-audit](data-audit.md), [model](model.md), [api-contract](api-contract.md), [architecture](architecture.md).
4. [implementation-plan](implementation-plan.md), [backlog.json](backlog.json), [reuse-research](reuse-research.md).
5. Для UI — обязательные design документы и [ui-plan](ui-plan.md); для приёмки — [test-plan](test-plan.md), [demo](demo.md). После начального ознакомления читать относящиеся к выбранной задаче разделы, а не весь комплект перед каждой правкой.

Использовать `.agents/skills/mvp-builder` для реализации, `demo-qa` для настоящей browser приёмки, `devops-deploy` только для относящегося к задаче контейнерного/разрешённого release шага. Skills дополняют прямое поручение и AGENTS; не придумывать дополнительные разрешения на рутинные исправления.

## Первый запуск

```powershell
git -c safe.directory=D:/localhost-3000 status --short
python scripts/mvp_coordination.py status
python scripts/mvp_coordination.py next
python scripts/profile_dataset.py
python scripts/check.py
git -c safe.directory=D:/localhost-3000 diff --check
```

Профилировщик только читает исходный fixture. Это не runtime input validator. `scripts/check.py` на этапе подготовки проверяет дизайн и probe; после замены probe нужно включить продуктовые проверки.

Не читать `.env` целиком в вывод, не печатать secrets. Подтвердить наличие Python/Docker/browser, порты и host-specific override; обычные локальные prerequisites готовить автономно в рамках выданного задания. Не заказывать новые сервисы ради реализации. Не исполнять `001_schema.down.sql` и не запускать генератор поверх оригинала. При создании демо-расширения писать в отдельный путь.

`artifacts/` игнорируется Git. Для будущей сдачи выбирать конкретные доказательства/спецификацию, а не добавлять всю папку; воспроизводимые текстовые сведения подготовки дополнительно сохранены в `docs/sources/`. Исходные материалы и пользовательские фото нельзя автоматически включать в коммит.

## Ownership при нескольких агентах

Прямой запуск команды разрешает настоящих worker/reviewer subagents по новой задаче пользователя. Внутренние роли не создают пользовательских чатов. По умолчанию у оркестратора один активный implementation claim; отдельные запуски проверяют общий реестр и независимость scopes/resources.

| Роль | Владеет | Не правит одновременно с координатором |
|---|---|---|
| Координатор | Выбор, план, ledger, согласование contracts и integration; код выполняет назначенный worker | Точные shared interface files бронирует до делегирования |
| Domain | `app/domain/**`, содержательные model tests | DTO/settings schema без согласования |
| Backend adapter | Отдельно назначенные `app/api/**`, auth/metrics tests | storage schema и main.py при занятом владельце |
| Frontend | `web/**`, browser journey source | `design/tokens.css`, общие ассеты и API contract без необходимости |
| Независимый reviewer | Read-only diff, тесты/контракты | Не исправляет втихую файлы другого работающего агента |

Количество агентов ограничено доступными слотами; обычный цикл — оркестратор, выделенный worker и свежий reviewer. Новый task получает нового worker, каждый review cycle — нового reviewer; тот же worker исправляет NO-GO своего claim. Точные пути добавляются через Extend до правки. Заготовки UI с mocks допустимы только до интеграции; mocks не остаются источником показателей.

## Как выбирать следующую задачу

`backlog.json` задаёт определения и зависимости, его статусы — исходный план. Текущее исполнение и принятые результаты брать из CLI/`.agent-state/mvp-coordination/claims.json`. Не переписывать backlog после каждого шага. Выбирать готовую задачу с проверенными зависимостями и незанятыми точными путями. B00 требует ответа о правилах перед конкурсным product development; запись «неизвестно» не является полученным ответом. Не переоткрывать уже подтверждённые решения; сохранять источник ответа через штатную gate-операцию.

Перед изменением прочитать существующую реализацию: у следующего агента код уже может быть частично готов. Документ не оправдывает перезапись рабочей версии по исходному плану. При отклонении улучшить минимально, обновить решения и контракт, затем проверять реальное поведение.

Для нового запуска написать `Выполняй план MVP`. Полный переносимый prompt и смысл короткой команды находятся в [EXECUTE_PLAN.md](EXECUTE_PLAN.md); AGENTS.md направляет туда будущий Codex.

Если у пользователя запрос на весь MVP, продолжать доступные задачи до цельного результата, не останавливаться на одном срезе ради формального отчёта. Перед новым этапом сообщать содержательный статус и оставшиеся вопросы, не запрашивать повторно уже выданные полномочия.

## Review и фиксация

Проверять diff на реальные источники ошибок: auth на всех маршрутах, Decimal/cents, unknown, отсутствие invented history, атомарность PUT/PATCH, persistence, согласованность UI/API/metrics, локальные Swagger assets, сохранение approved tokens. После product slice запустить нужные тесты и реальный browser путь.

Обязательное перед коммитом: `python scripts/check.py`, `git diff --check`; коммит только просмотренных конкретных путей. Настройка workflow включает отдельный локальный checkpoint планирования/координатора. После прямого запуска команды локальные checkpoints входят в работу по образцу MTCH; одно чтение плана ничего не запускает. Push/PR/публикация требуют своего поручения. Для передачи/релиза проверить актуальный контекст доступа и состояние инфраструктуры, а evidence сохранять раздельно по local/Docker/CI/VPS/HTTPS/E2E.

В отчёте: что изменилось для пользователя, почему, чем проверено, что осталось. Нельзя пометить B10/A-12 выполненными, показав только unit tests, API lifecycle или статичный prototype.
