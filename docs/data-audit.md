# Аудит предоставленных данных

Дата проверки: 23 октября 2026 года. Исследована локальная копия `материалы/data/`; исходные файлы не изменялись. Это анализ данных и подготовка реализации, не проверка готового продукта.

## Главный вывод для реализации

Данные подходят для загрузки DTO, разработки панели, объяснимой модели правил и воспроизводимых проверок. Они **не содержат размеченного оттока и не позволяют обучить или измерить качество прогностической ML-модели**. В ТЗ прямо сказано, что предоставлен текущий снимок, история статусов и даты удаления отсутствуют, а способ расчёта выбирает команда (`материалы/ТЗ.pdf`, стр. 2, 13; извлечение: `artifacts/planning/brief-extracted.txt:11–24,163–177`).

Предлагаемая стратегия команды: объяснимый индекс риска с редактируемыми весами, явным `unknown` и объяснением ограничений. Значение `score / 100` в денежной формуле — выбранный коэффициент сценарного взвешивания, а не статистически подтверждённая вероятность оттока. Не обещать ROC-AUC, точность прогноза, калибровку, доказанный uplift или исторический backtest на этих данных.

Часть значений противоречит описанному в ТЗ жизненному циклу. Анализатор должен сохранить исходный снимок, показать предупреждения качества и вычислить результат по документированной политике. Исправлять `status`, даты или балансы в оригиналах для получения красивой демонстрации нельзя.

## Смысл полей: ТЗ и решения команды

| Поле / статус | Установлено ТЗ | Следствие для проектируемого анализатора |
| --- | --- | --- |
| Все суммы | Еврокопейки; €1 = 100 единиц (стр. 4) | Хранить и считать в целых единицах; не смешивать евро и cents |
| `balance` | Реальные деньги на основном балансе (стр. 4) | Учитывать для оплаты ближайшей общей корзины продлений |
| `withdrawBalance` | Реферальные деньги, доступные для вывода либо перевода на баланс (стр. 4) | Предложение команды: не считать автоматически доступными для автосписания до перевода |
| `bonusBalance`, `bonusState` | Бонусы тратятся на услуги, `bonusState` задаёт доступность (стр. 4) | Предложение: доступные средства `balance + (bonusBalance, если unlocked)`; `locked` не увеличивает покрытие |
| `totalReplenished` | Все пополнения реальными деньгами за всё время (стр. 4) | Это не текущая выручка, не MRR и не размеченный LTV |
| `active` | Услуга активна и приносит деньги (стр. 3) | Допускать в прогноз ближайших продлений |
| `suspended` | Выключена пользователем, деньги продолжают начисляться (стр. 3) | Не исключать из будущей выручки как уже потерянную услугу |
| `prolong_wait` | Истёк `expiresAt`; ожидание оплаты 5 дней, затем `deleted` (стр. 3) | Сигнал риска; превышение 5 дней отдельно показывать как качество входных данных |
| `blocked` | Продление и использование невозможны (стр. 3) | Предложение: исключать из предстоящих возобновляемых услуг |
| `deleted` | Удалена из-за неуплаты либо по желанию клиента (стр. 3) | Не выдавать за предстоящее непродление и не выводить причину удаления без данных |
| `not_performed` | Транзакция пока или вовсе не исполнена, например неоплаченный заказ (стр. 5) | Не приравнивать автоматически к банковской ошибке или состоявшемуся оттоку |

Точные извлечённые строки: `artifacts/planning/brief-extracted.txt:30–53,56–68`. Статусы `locked`/`unlocked` взяты из предоставленного DTO (`материалы/data/data.json:10,19`); PDF объясняет смысл `bonusState`, но не перечисляет эти строковые значения.

ТЗ описывает флаг как `autoprolong`, тогда как JSON и SQL используют `autoProlong` (`artifacts/planning/brief-extracted.txt:57`; `материалы/data/data.json:101`; `материалы/data/001_schema.up.sql:21`). Входной контракт следует привязать к фактическому DTO `autoProlong`, обозначив различие в OpenAPI; не создавать два расходящихся поля.

## Обнаруженные ограничения и несоответствия

### 1. Снимок не является бухгалтерской историей

README прямо предупреждает: балансы не вычисляются из транзакций, история пополнений отсутствует, `amount` независим от `price` (`материалы/data/README.md:62–63`). Проверено: **100 из 100** транзакций имеют сумму, не равную цене своей услуги (`artifacts/planning/data-profile.json:306`). Это не следует исправлять пересчётом балансов по транзакциям.

Все 70 `prolong` созданы раньше текущего `expiresAt`; 34 из них — даже раньше `order` соответствующей услуги (`artifacts/planning/data-profile.json:307–344`). Генератор создаёт каждую транзакцию в пределах 0–5 минут от первоначального создания услуги, независимо от номера продления (`материалы/data/generate.py:63–73`). Продление до окончания само по себе может быть допустимо; комбинация времён и независимых сумм не позволяет считать этот набор последовательным журналом оплаченных периодов.

### 2. Время и статусы расходятся

Все шесть `prolong_wait` уже на опорной дате старше разрешённых в ТЗ пяти дней: услуги 5, 10, 15, 20, 25, 30 — примерно 219, 309, 370, 393, 400 и 35 дней после `expiresAt`. Причина — генератор создаёт эти услуги за 400 дней до reference и прибавляет ровно один период (`материалы/data/generate.py:48–59`; примеры `материалы/data/data.json:140–148,415–423`; IDs в `artifacts/planning/data-profile.json:371–378`).

При расчёте на `2026-10-23T00:00:00Z` услуга 1 остаётся `active`, хотя её `expiresAt = 2026-10-19T15:30:00Z` уже прошёл (`материалы/data/data.json:96–104`; воспроизведение командой профиля с `--reference`). Значит, запуск на реальных часах меняет временные признаки. Нужны инъекция часов в тестах, видимая дата расчёта и отдельное объяснение устаревшего снимка. Анализатор не должен сам выполнять обязанности биллинга и переводить услуги между статусами.

### 3. В наборе нет многих ключевых ситуаций приёмки

Каждый основной баланс больше цены любой отдельной услуги. Более того, **у каждого аккаунта баланс больше суммы цен всех его трёх услуг** (`artifacts/planning/data-profile.json:349,385`). При модели «одно следующее продление услуги» fixture не проверяет нехватку средств даже без бонусов. На длинном горизонте с повторениями почасовых услуг вывод может измениться; это уже другая денежная модель и другой знаменатель.

Нет аккаунта без услуг, нет пустых коллекций, нет смешанных статусов транзакций одной услуги, нет обычных названий на кириллице, нет искусственно отрицательных входов для API (`материалы/data/generate.py:35–74`). Значит, использовать только исходный JSON для acceptance недостаточно. ТЗ разрешает расширить тестовый набор для наглядности (`материалы/ТЗ.pdf`, стр. 8; `artifacts/planning/brief-extracted.txt:104–108`).

### 4. Искусственные зависимости создают утечки и ложные выводы

Генератор циклически выбирает категориальные поля: `bonusState` по чётности ID, `status` услуги по ID modulo 5, `paymentTerm` по ID modulo 6, `ownerId` по ID modulo 10, статус транзакции по ID modulo 3 (`материалы/data/generate.py:42,46–47,56,63–70`). В результате:

- Все три услуги одного владельца имеют один и тот же статус.
- Все транзакции одной услуги имеют один и тот же статус исполнения.
- `serviceId`, `id` и `ownerId` могут «предсказывать» искусственную категорию без бизнес-смысла.

Это видно в `artifacts/planning/data-profile.json:345–348`. Идентификаторы и email нельзя использовать как признаки оттока. Случайное разбиение связанных транзакций на train/test создаст видимость качества на родственном синтетическом материале; настоящего целевого признака оттока всё равно нет.

### 5. SQL fixture вводит ограничения, которых нет в PDF

| Ограничение fixture | Основание | Решение для будущего API |
| --- | --- | --- |
| `name ~ ^[A-Za-z0-9-]+$` | `материалы/data/001_schema.up.sql:16`; README:57 | PDF на стр. 5 называет имя произвольным. Принимать обычный Unicode и безопасно отображать его как текст; не переносить regex в продукт как требование организаторов |
| `amount BETWEEN 0 AND 1000` | `материалы/data/001_schema.up.sql:37`; README:55 | На стр. 5 PDF есть только смысл `amount`, без верхнего предела. Сумма €10,01 не должна отклоняться только из-за fixture; предел типа и размер входа определить отдельно |
| `withdrawBalance <= balance`, `totalReplenished >= balance` | Генератор соблюдает; README:62 прямо говорит, что схема этого не требует | Не навязывать эти отношения импорту: реферальный баланс и основной баланс имеют разный смысл |
| Все даты должны иметь именно `.000Z` | Генератор/README форматируют UTC с миллисекундами | Строгий формат fixture не заменяет решение о допустимом ISO 8601 в OpenAPI; нормализовать валидные timezone timestamps к UTC |

`scripts/profile_dataset.py` отдельно помечает отклонения от regex/лимита суммы как ограничения **fixture SQL**, а не ошибки универсального продуктового контракта. Он также проверяет точный формат и набор полей исходного fixture; его не следует подключать напрямую как валидатор `/source/snapshot`.

### 6. Нет истории, меток и нескольких необходимых знаменателей

В DTO отсутствуют `churned`, дата отказа, дата удаления, история переходов, история пополнений, логины/посещения, дата регистрации аккаунта, обращения поддержки, результаты маркетинговых действий. Нельзя восстановить по нему:

- Реальный churn rate за день/неделю, retention-когорты, накопленные удаления по датам.
- Последнюю активность человека по `transactions.createdAt`: это время заказа/продления, а не посещения.
- Реальный LTV, стоимость удержания и эффект маркетингового воздействия.
- Причину удаления: неуплата и инициатива клиента объединены одним статусом.

Текущий `deleted` — факт текущего состояния, но дата этого факта неизвестна. Для дополнительного исторического графика допустимо начать сохранять наблюдения **после запуска** с явной подписью «наблюдается с …». Время получения нового snapshot не следует называть доказанным временем удаления; между двумя наблюдениями событие могло произойти раньше. Будущий прогноз следует визуально отделять от наблюдаемого ряда (ТЗ, стр. 2 и 13).

### 7. Происхождение и обращение с данными

Адреса в исходном JSON имеют тестовый вид `user-0001@example.test`; имена услуг тоже синтетические (`материалы/data/generate.py:38,55`). Аудит выполнен локально, данные во внешние модели и сервисы не передавались. В перечисленных семи файлах комплекта нет отдельного файла лицензии; требование использовать комплект в решении содержится в ТЗ на стр. 2 и 8, но это не основание подписывать его произвольной open-source лицензией или обещать права на дальнейшее публичное распространение.

Даже с вымышленными email панель и API должны быть защищены согласно ТЗ. Не выносить email, ID клиентов и названия услуг в Prometheus labels: агрегированные счётчики не требуют таких данных. Отсутствие настоящих персональных данных в fixture не отменяет проверку доступа к обязательным endpoint.

## Рекомендуемый план обращения с данными

Это проектные предложения команды, а не новые требования организаторов.

1. Сохранить исходники неизменными; использовать `data.json` как исходный seed. Для демонстрационных расширений создать отдельные файлы с явным происхождением.
2. Сначала реализовать атомарную валидацию и полную замену snapshot. Проверить структуру, связи, уникальные ID, денежные единицы, допустимые статусы, корректность дат и ограничения размера. При ошибке не менять текущую рабочую версию.
3. Не выполнять произвольный SQL из загружаемого источника. Endpoint принимает DTO; SQL комплекта нужен только для известной одноразовой начальной загрузки в специально выбранную БД.
4. Нормализовать UTC и хранить метаданные `snapshotVersion`, `receivedAt`, `analysisAt`, `modelVersion`; они создаются приложением и не выдаются за неизвестную историю источника.
5. Разделить ошибки структуры и предупреждения качества. Длительный `prolong_wait`/`active` после срока не должны приводить к тихой подмене исходного статуса.
6. Для признака покрытия средств учитывать **общую корзину** учитываемых ближайших продлений аккаунта; не сравнивать каждую услугу с одним и тем же полным балансом независимо и не списывать его несколько раз.
7. Для account score документировать агрегацию service score. Предложение команды: максимум по пригодным услугам; при отсутствии таких услуг `score=null`, `level=unknown` с причиной. В текущем fixture аккаунты 2, 3, 7, 8 имеют только `blocked`/`deleted` (`artifacts/planning/data-profile.json:379–384`).
8. Денежную оценку считать по ценам следующего выбранного периода учитываемых услуг с факторами риска; не складывать `balance`, `withdrawBalance` или `totalReplenished` в сумму потерь. Балансы влияют на риск покрытия. Подпись должна говорить о сценарной валовой стоимости ближайших продлений, а не о доказанной потере cash flow.
9. Отдавать панель, summary и Prometheus по одной согласованной версии данных/модели, чтобы разные представления не показывали разные суммы во время пересчёта.

В исходной схеме ID имеют тип PostgreSQL `bigint`; текущие значения малы. При переходе к реальным ID заранее определить безопасное представление в JavaScript/JSON, чтобы не потерять точность выше `2^53−1` (`материалы/data/001_schema.up.sql:4,15,36`). Это техническое ограничение реализации, не обнаруженная ошибка имеющихся ID.

## Минимальная матрица дополнительных тестовых снимков

Генератор большого случайного набора не заменяет адресные сценарии. Расширения должны отличаться от оригиналов и иметь фиксированную дату анализа.

| Сценарий | Изменение отдельной тестовой копии | Проверяемое поведение |
| --- | --- | --- |
| Скорое окончание | `active`, срок внутри горизонта, `autoProlong=false` | Увеличение соответствующего сигнала и конкретное объяснение |
| Не хватает на корзину | Две пригодные услуги; денег хватает на одну, но не на обе | Общий дефицит, без двойного использования одного баланса |
| Бонус доступен | Одинаковый клиент и услуги, `locked → unlocked` | Покрытие меняется только на разрешённую сумму бонусов |
| Реферальные деньги | Менять только `withdrawBalance` | Автопокрытие не растёт без перевода на основной баланс |
| Услуга выключена | `active → suspended`, та же цена | Она сохраняет денежную значимость согласно ТЗ |
| Ожидание оплаты | `prolong_wait`, прошло 1–4 дня, низкий баланс | Сигнал ожидания оплаты и дефицита без ошибки качества |
| Неконсистентный источник | `prolong_wait`, прошло больше 5 дней | Предупреждение о статусе; исходная услуга не переписывается |

| Пустой корректный снимок | Все три массива пусты | Пустое состояние панели, нулевые агрегаты, отсутствие NaN |
| Смена коэффициента | Те же данные, иной вес включённого признака | Изменение расчёта/рейтинга/денег без reload и совпадение метрик |

| Легитимные данные вне fixture | Кириллица в `name`, `amount=1001`, Unicode email при выбранной политике | Нет необоснованного regex/лимита из генератора; политика email описана отдельно |

## Импорт SQL и воспроизводимость

Начальная схема и seed используют разные транзакции. Seed блокирует три таблицы, проверяет их пустоту, загружает JSON recordset, затем выставляет последовательности по max(id). Он **откажется** работать поверх непустых таблиц (`материалы/data/002_seed.sql:1–10`; `материалы/data/generate.py:79–95`). Поэтому seed не реализует семантику полной замены снимка из обязательного `PUT /api/v1/source/snapshot`.

`001_schema.down.sql` удаляет таблицы с данными; это rollback одноразового fixture, а не способ обновлять приложение (`материалы/data/001_schema.down.sql:1–6`). В ходе аудита не запускался.

В памяти проверено: `generate(10, 30, 100, 42, reference)` точно совпадает с предоставленным объектом JSON; `seed_sql(data)` совпадает с SQL после нормализации переводов строк при чтении. Сравнение recordset каждого из трёх массивов также совпало (`artifacts/planning/data-profile.json:389–398`). Исходный SHA всех семи файлов до/после аудита одинаков.

Не запускать `generate.py` с `--out` по умолчанию из `материалы/data`: он перезапишет `data.json` и `002_seed.sql` (`материалы/data/generate.py:105,117–119`). Для новых объёмов использовать отдельный явно указанный каталог и сохранять seed/reference в метаданных.
