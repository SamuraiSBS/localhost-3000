# Автономная реализация «Лаборатории решений»

Статус: редакция 5 от 25 октября 2026 года. Продуктовый объём включает B15–B25, внутренние domain-срезы B26–B29 и preflight-support B31; по прямому уточнению пользователя B12 и проверки только дизайна/вёрстки отложены. Создание или цитирование инструкции не запускает реализацию. Продуктовый scope открывает прямое поручение выполнить команду.

## Команда для чата проекта

Скопировать целиком в текущий или новый чат с рабочей папкой `D:\localhost-3000`:

```text
В текущем чате автономно выполни план «Лаборатория решений» по docs/DECISION_LAB_PLAN.md и процедуре docs/EXECUTE_DECISION_LAB.md до принятия финальной B22 со всеми зависимостями B15–B29. Включи оба направления: проверку модели жюри и практический план действий маркетолога, включая минимальное действие, предпросмотр импорта и воспроизводимый паспорт решения. Начни с preflight и сверки редакции задач из docs/decision-lab-backlog.json с существующим backlog по описанным правилам, сохрани B00–B14. Используй существующий координатор, отдельного worker на задачу и нового независимого reviewer на каждый цикл. Продолжай через исправления, реальные браузерные проверки и проверку нового локального ZIP. Сохраняй чужие изменения и принятый MVP; B12 и дизайн/вёрстка отложены, реализуй функции с простыми controls; обязательны реальные функциональные browser checks и новый локальный ZIP. Разрешены необходимые локальные сервисы, task-owned setup и небольшие проверенные локальные commits. Не делай push, публичный deploy, внешние сообщения, покупки и изменения DNS/доступов. Не останавливайся после первого работающего среза; при реальном blocker сохрани точное состояние и продолжай доступные независимые задачи. Эта команда разрешает обычную передачу ownership оркестратора в текущий чат по штатной процедуре, но не recovery недоступных workers и не обход gates.
```

Точка входа осталась прежней: «В текущем чате выполни полную команду автономной реализации из docs/EXECUTE_DECISION_LAB.md по плану docs/DECISION_LAB_PLAN.md». Её старое продолжение «до приёмки B15–B22» также означает приёмку финальной B22 с актуальными зависимостями, включая B23–B29. B26–B29 — внутреннее разделение реализации, без новых пользовательских функций.

Это самостоятельное расширение scope после MVP. Короткая команда «Выполняй план MVP» сама по себе по-прежнему ограничена своим прежним объёмом. Команда лаборатории включает B15–B25 и внутренние domain-срезы B26–B29, без фоновой автоматизации и без создания пользовательских чатов для внутренних ролей. Дополнительный preflight-support B31 нужен только для разрешённого snapshot recovery. Порядок: B15 → B16 → параллельно B17 и B26–B29 → B18 → B19 → B20 → B23 → B24 → B25 → B21 → B22; каждый интеграционный этап ждёт свою domain-зависимость. B12 отложен, окончание на B20 или старой версии B22 не завершает новый scope.

### Уточнение пользователя от 25 октября 2026 года

B12 и повторная проверка графика отложены. B15 не должен зависеть от B12; B11 и B13 остаются зависимостями. Реализация использует простые функциональные controls. Не выполнять и не принимать пункты, результатом которых является только оценка дизайна, композиции или вёрстки. Реальные browser journeys по функциям, ошибки/409/stale и проверка ZIP остаются обязательными.

B26–B29 — только внутренние чистые domain-модули и unit-тесты для существующих функций B20/B23/B24/B25. Они зависят от B16, не редактируют общие DTO/API/OpenAPI/UI и могут выполняться параллельно с B17 по непересекающимся точным paths.

## 1. Preflight и подготовка плана

1. Прочитать корневой AGENTS, [план](DECISION_LAB_PLAN.md), [набор задач](decision-lab-backlog.json), START_HERE и относящиеся model/API/architecture/design документы. Использовать актуальные правила, а не устаревшие статусы заголовков; `hackathon-planner` — подготовка, `mvp-builder` — реализация, `demo-qa` — браузерная приёмка.
2. Проверить git status, staged/untracked, ветку, доступных агентов, live coordinator `status`/`next`, владельца, claims, snapshots и named resources. Большой JSON статуса сворачивать до нужных полей; не печатать секреты или окружение. Получать только точечный `CODEX_THREAD_ID` для identity.
3. Убедиться в актуальности baseline B11 и B13 по coordinator и фактическим файлам. B12 не переоткрывать и не проверять в этом запуске по прямому уточнению пользователя. Новый план не делает чужие dirty bytes принятыми. Обнаруженную несовместимость или потерю lineage для B11/B13 оформить с точными путями/хешами; не восстанавливать чужие файлы и не переписывать acceptance. Не обходить dirty/snapshot gates. Требуемая авторизация чужой работы не подразумевается.
4. Если этот запуск не совпадает с владельцем ledger, штатный `handoff` возможен только без active attempts и с fresh source evidence приведённого прямого поручения пользователя. Не подставлять прежний run ID. Активный/неизвестный worker остаётся занятым; recovery требует отдельного прямого разрешения по действующей процедуре.
5. До изменения основного backlog убедиться, что нет active attempts: добавление задач изменяет общий plan hash. Проверить, что сам backlog не содержит чужого dirty изменения. При конфликте сохранить подготовленный набор и зафиксировать blocker; не изменять план под работающим claim.
6. Сверить `plan_revision` и `registration_updates` подготовленного набора с `docs/backlog.json.tasks`. В редакции 5 отсутствующий B31 добавляется как отдельная P0 preflight-support задача; отсутствующие B15–B29 добавляются как продуктовые и внутренние domain-задачи. Для каждого обновления B15/B19/B20/B21/B23/B24/B25 вычислить coordinator task hash текущего определения и подготовленного target из `tasks`: точное совпадение с target означает, что обновление уже применено, и является no-op; иначе обновление разрешено только при точном совпадении current hash с указанным `expected_previous_task_hash`. При применении target сохранять существующие status/evidence. Любой другой hash — конфликт, а не разрешение перезаписать чужой план. B00–B14, верхний `contract_documents` и остальные определения не менять; не подменять основной backlog файлом расширения. Никаких ручных изменений ledger.
7. Проверить JSON, зависимости и coordinator `next`. Если актуализация backlog сделала прежнюю B14-приёмку stale по точному manifest, выполнить новую попытку с тем же определением и task hash, сохранив историю и получив свежий independent review. B31 и ранее принятые задачи открывать повторно только если это требует актуальный ledger. После checkpoint выбирать только whitelist B15–B29; B15 зависит от B11/B13, B12 отложен. `ready_p1` — имя поля координатора, а не причина выходить за whitelist. B00–B14 definitions и история остаются на месте. Если изменяемая задача уже принята, её прежний GO не переносить на новое определение.
8. Подготовленные документы, добавление задач и только проверенные принадлежащие этой работе пути сохранить отдельным локальным checkpoint до первого Claim. Ветка по правилам проекта, например `feat/decision-lab`; не переключать её и не менять общий HEAD/index при live claims. Не включать чужой staged/dirty scope. Перед commit обязательны `python scripts/check.py` и `git diff --check`; отказ проверки не обходить.

### Preflight-support B31 для разрешённого snapshot recovery

- Пользователь прямо разрешил разработать отдельный reviewed recovery с сохранением исходного snapshot. Это разрешение не меняет уже принятую задачу B14 и не разрешает менять либо пересоздавать исходные snapshot/recovery-записи.
- Выполнить B31 отдельными worker, новым независимым reviewer и root Accept. B31 может предложить recovery только для точного `ac1a0c41-a76b-46c6-84f2-aa2008ae2837`, сохраняя его исходный manifest и provenance. B14 сохраняет прежнюю семантику.
- После B31 Claim worker применяет сохранённый пользовательский патч `AGENTS.md` из `artifacts/acceptance/b12-agents-parallel-commit-source.md` внутри claimed scope. После фиксации этих bytes, но до первого candidate, root делает одно начальное предложение с прямой авторизацией пользователя и точным текущим manifest двух snapshot-путей. После предложения bytes `AGENTS.md` и `components.json` заморожены до Accept; B31 не поддерживает amendment или continuation. Любой drift блокирует Submit/Accept.
- Если добавление B31 обновило manifest принятой B14, сначала завершить same-definition B14 GO/Accept и отдельный commit только если есть принятые новые bytes; при no-op не создавать пустой commit и сохранить прежнюю SHA с причиной.
- B31 Accept и отдельный exact-path commit должны завершиться до нового B15 Claim. Если B31 меняет рабочий код или manifest после proposal, действовать только через предусмотренные gates; не переписывать ledger и не ослаблять валидатор.
- B31 разблокирует preflight, но не входит в продуктовую последовательность и не считается завершением команды.

На этапе подготовки запрещены правки продуктового кода. Не менять координатор, не создавать второй ledger и не переинициализировать существующее state. Набор редакции 5 — обновление плана, не фиктивное состояние исполнения. Перед каждым новым Reserve сверять его с основным backlog; изменения plan hash проводить только без active attempts или через обязательный Rebase и свежий review.

## 2. Реализация и независимое review

Следовать [основной процедуре](EXECUTE_PLAN.md), [оркестратору](coordination/orchestrator.md) и [реальным CLI-флагам](coordination/cli-reference.md), с явным scope B15–B29:

```text
fresh readiness → same-definition B14 revalidation if stale → B31 accepted and committed → B15 → B16
→ parallel batch: B17 + B26 + B27 + B28 + B29 (disjoint exact paths/resources)
→ B18 → B19 → B20 → B23 → B24 → B25 → B21 → B22
→ for each task: Reserve exact paths/resources → spawn worker → Bind actual ID
→ Check → Claim → implement/test → Submit
→ spawn fresh read-only reviewer → Bind reviewer → GO / NO_GO
→ same worker repairs + new reviewer if NO_GO → orchestrator Accept
→ checkpoint when no active attempts → next readiness → next task
```

- Под каждую задачу создавать настоящего внутреннего subagent worker; для каждого цикла — нового независимого reviewer. `collaboration` используется вместо новых пользовательских чатов. Реальные target/run UUID и tool evidence обязательны.
- `suggested_paths` — кандидаты, не право правки. Перед Reserve сформировать конечный точный список существующих/новых файлов, tests, docs, evidence и generated outputs. Wildcard/папка не являются claim scope. Аналогично зарезервировать настоящий порт, runtime/browser session и task-owned temp/data directory. Не использовать чужой контейнер/том/сеанс для тестов.
- При dirty внутри нужного файла разрешено только подтверждённое совпадение с последним accepted lineage через штатный `--adopt-accepted`. Чужие изменения и snapshot drift не легализуются командой, общим checkpoint или обещанием сохранить их. Согласовать их с владельцем либо продолжить непересекающуюся часть; не отключать проверку.
- После Accept и отдельного commit B16, одновременно открыть весь готовый непересекающийся набор B17/B26–B29 при доступных native slots и разных runtime resources. После этого общие integration paths задают последовательные зависимости. Сверять полный ready-front и claims при каждом освобождении слота; commit barrier и точные отдельные commits обязательны.
- Worker применяет только свой scope. Расширение — через Extend; изменение плана — без live attempts либо с обязательным Rebase и новым review по процедуре. Изменение основного `contract_documents` инвалидирует принятие зависимостей: предпочесть отдельные feature-контракты и отчёты.
- Результат Submit должен относиться к текущему plan hash, iteration и exact manifest. После NO_GO исправляет тот же worker; следующий reviewer новый. Только оркестратор принимает совпавший GO. Проверки или один отчёт worker не означают accepted.
- Полное соответствие этому feature-плану проверяет reviewer, включая `scope_plan` каждого task. При изменении согласованных требований сначала обновить план/определения вне live attempts, зафиксировать diff и заново проверить затронутые результаты.

## 3. Проверки и результат

- B15 фиксирует полный контракт редакции 2, включая solver, preview/подтверждение импорта и case/replay, разумные лимиты и контрольные fixtures; значения и названия из плана — основа, а не повод спрашивать разрешение на обычные детали реализации.
- B18 проверяет отдельно rank stability при изменении весов и label stability при изменении порогов. Варианты порогов запрещено включать в знаменатель top-K.
- B23–B25 выполняются перед B21/B22. Preview/solver/replay не пишут рабочие данные; подтверждение импорта B24 — единственный новый явный writer через существующий coordinator-путь, с атомарной проверкой baseline/checksum и прежней защитой API. Экспорт не означает публикацию или отправку кому-либо.
- Проверять чистые функции, shared funds, Decimal/cents, unknown, невмешательство в рабочее состояние, revisions/409, детерминизм, auth/CSRF и действующие обязательные маршруты. На изменение — подходящие unit/integration checks; перед commits — полный проектный check и whitespace check.
- В B21 пройти функциональные L01–L13 и L15–L19 через нужные тесты и реальный доступный browser tool. Проверять реальные действия, keyboard controls, ошибки/409/stale; дизайн, layout, responsive, zoom и motion checks пропустить. API не заменяет browser evidence. Сохранять версии, реальные команды, результаты, скриншоты и ограничения в task-owned `artifacts/acceptance/decision-lab/`.
- Обычную нехватку runtime/браузера/локальных зависимостей устранять в разрешённом task-owned scope. Не менять ACL, не подменять данные и не обходить согласие или credentials. При реальном внешнем blocker записать `failed/not_run`, источник и следующий допустимый шаг. Заблокированная задача удерживает резерв; таймер не доказывает остановку worker.
- В B22 выполнить L14/L20: обновить точный package allowlist всеми новыми runtime/UI файлами и feature-документами, экспорт OpenAPI, подготовить новый ZIP с отдельным именем и checksum. Не перезаписывать прежний candidate. Проверить запуск из распакованного ZIP с чистым browser profile и отдельными task-owned data/портом; не брать assets из кеша checkout. Сохранить действующие ограничения распространения секретов, шрифта, фото и исходных материалов.
- Все B15–B25, внутренние domain-срезы B26–B29 и функциональные L01–L20 входят в итоговый результат; B12 и чисто визуальные/верстальные проверки исключены по прямому уточнению пользователя. Если часть функционального объёма не принята, назвать её незавершённой. Итог содержит accepted IDs, commits, worker/reviewer IDs, evidence, путь/checksum нового ZIP и ограничения. Публичная доступность и передача не входят в команду и не подразумеваются.

Если сеанс завершился, повтор той же команды заново сверяет актуальное состояние и продолжает существующие задачи. Нельзя обещать продолжение в фоне без отдельной автоматизации.
