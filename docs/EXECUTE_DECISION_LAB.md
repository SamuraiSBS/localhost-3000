# Автономная реализация «Лаборатории решений»

Статус: инструкция подготовлена 24 октября 2026 года. Её создание или цитирование не запускает реализацию. Продуктовый scope открывает прямое поручение пользователя выполнить приведённую ниже команду.

## Команда для чата проекта

Скопировать целиком в текущий или новый чат с рабочей папкой `D:\localhost-3000`:

```text
В текущем чате автономно выполни план «Лаборатория решений» по docs/DECISION_LAB_PLAN.md и процедуре docs/EXECUTE_DECISION_LAB.md до принятия B15–B22. Включи оба направления: проверку модели жюри и практический план действий маркетолога. Начни с preflight и регистрации задач из docs/decision-lab-backlog.json в существующем backlog без изменения прежних задач. Используй существующий координатор, отдельного worker на задачу и нового независимого reviewer на каждый цикл. Продолжай через исправления, реальные браузерные проверки и проверку нового локального ZIP. Сохраняй чужие изменения, принятый MVP, график, OIDC и Digital Ruins. Разрешены необходимые локальные сервисы, task-owned setup и небольшие проверенные локальные commits. Не делай push, публичный deploy, внешние сообщения, покупки и изменения DNS/доступов. Не останавливайся после первого работающего среза; при реальном blocker сохрани точное состояние и продолжай доступные независимые задачи. Эта команда разрешает обычную передачу ownership оркестратора в текущий чат по штатной процедуре, но не recovery недоступных workers и не обход gates.
```

Это самостоятельное расширение scope после MVP. Короткая команда «Выполняй план MVP» сама по себе по-прежнему ограничена своим прежним объёмом. Новая команда включает все B15–B22, без фоновой автоматизации и без создания пользовательских чатов для внутренних ролей.

## 1. Preflight и подготовка плана

1. Прочитать корневой AGENTS, [план](DECISION_LAB_PLAN.md), [набор задач](decision-lab-backlog.json), START_HERE и относящиеся model/API/architecture/design документы. Использовать актуальные правила, а не устаревшие статусы заголовков; `hackathon-planner` — подготовка, `mvp-builder` — реализация, `demo-qa` — браузерная приёмка.
2. Проверить git status, staged/untracked, ветку, доступных агентов, live coordinator `status`/`next`, владельца, claims, snapshots и named resources. Большой JSON статуса сворачивать до нужных полей; не печатать секреты или окружение. Получать только точечный `CODEX_THREAD_ID` для identity.
3. Убедиться в актуальности baseline B11/B12/B13 по coordinator и фактическим файлам. Известное наблюдение revision 208 записано в плане: B12/B13 сейчас неактуальны по accepted lineage; перечитать его перед запуском. Новый план не делает чужие dirty bytes принятыми. Обнаруженную несовместимость или потерю lineage оформить с точными путями/хешами; не восстанавливать чужие файлы и не переписывать acceptance. Команда включает штатную повторную проверку этих зависимостей через их существующие задачи после подтверждения допустимого ownership/provenance; не менять определения B00–B14 и не обходить dirty/snapshot gates. Требуемая авторизация чужой работы не подразумевается.
4. Если этот запуск не совпадает с владельцем ledger, штатный `handoff` возможен только без active attempts и с fresh source evidence приведённого прямого поручения пользователя. Не подставлять прежний run ID. Активный/неизвестный worker остаётся занятым; recovery требует отдельного прямого разрешения по действующей процедуре.
5. До изменения основного backlog убедиться, что нет active attempts: добавление задач изменяет общий plan hash. Проверить, что сам backlog не содержит чужого dirty изменения. При конфликте сохранить подготовленный набор и зафиксировать blocker; не изменять план под работающим claim.
6. Добавить в `docs/backlog.json.tasks` только определения B15–B22 из подготовленного набора. Не менять верхний `contract_documents`, метаданные и прежние task definitions; не подменять backlog файлом расширения. Если IDs уже существуют, сравнить полные определения без runtime status/evidence: совпадающие не дублировать, несовпадающие требуют разрешения конфликта. Никаких ручных изменений ledger.
7. Проверить JSON, зависимости и coordinator `next`. Он называет все non-P0 готовые задачи `ready_p1`, поэтому выбирать только whitelist B15–B22, а не полагаться на имя поля. Приёмка B00–B14 не должна теряться из-за изменения их определений/основных контрактов.
8. Подготовленные документы, добавление задач и только проверенные принадлежащие этой работе пути сохранить отдельным локальным checkpoint до первого product Claim. Ветка по правилам проекта, например `feat/decision-lab`; не переключать её и не менять общий HEAD/index при live claims. Не включать чужой staged/dirty scope. Перед commit обязательны `python scripts/check.py` и `git diff --check`; отказ проверки не обходить.

На этапе подготовки запрещены правки продуктового кода. Не нужно менять координатор ради другого backlog, создавать второй ledger или инициализировать существующее state заново. Сейчас задачи подготовлены отдельным JSON именно потому, что пользователь заказал план и команду, а не запуск исполнения.

## 2. Реализация и независимое review

Следовать [основной процедуре](EXECUTE_PLAN.md), [оркестратору](coordination/orchestrator.md) и [реальным CLI-флагам](coordination/cli-reference.md), с явным новым scope B15–B22:

```text
fresh readiness → Reserve exact paths/resources → spawn worker → Bind actual ID
→ Check → Claim → implement/test → Submit
→ spawn fresh read-only reviewer → Bind reviewer → GO / NO_GO
→ same worker repairs + new reviewer if NO_GO → orchestrator Accept
→ checkpoint when no active attempts → next readiness → next task
```

- Под каждую задачу создавать настоящего внутреннего subagent worker; для каждого цикла — нового независимого reviewer. `collaboration` используется вместо новых пользовательских чатов. Реальные target/run UUID и tool evidence обязательны.
- `suggested_paths` — кандидаты, не право правки. Перед Reserve сформировать конечный точный список существующих/новых файлов, tests, docs, evidence и generated outputs. Wildcard/папка не являются claim scope. Аналогично зарезервировать настоящий порт, runtime/browser session и task-owned temp/data directory. Не использовать чужой контейнер/том/сеанс для тестов.
- При dirty внутри нужного файла разрешено только подтверждённое совпадение с последним accepted lineage через штатный `--adopt-accepted`. Чужие изменения и snapshot drift не легализуются командой, общим checkpoint или обещанием сохранить их. Согласовать их с владельцем либо продолжить непересекающуюся часть; не отключать проверку.
- Обычно идти последовательно: соседние задачи используют одни integration paths. Параллельность выводить из зависимостей, свободных native slots, точных paths/resources; фиксированного искусственного лимита нет.
- Worker применяет только свой scope. Расширение — через Extend; изменение плана — без live attempts либо с обязательным Rebase и новым review по процедуре. Изменение основного `contract_documents` инвалидирует принятие зависимостей: предпочесть отдельные feature-контракты и отчёты.
- Результат Submit должен относиться к текущему plan hash, iteration и exact manifest. После NO_GO исправляет тот же worker; следующий reviewer новый. Только оркестратор принимает совпавший GO. Проверки или один отчёт worker не означают accepted.
- Полное соответствие этому feature-плану проверяет reviewer, включая `scope_plan` каждого task. При изменении согласованных требований сначала обновить план/определения вне live attempts, зафиксировать diff и заново проверить затронутые результаты.

## 3. Проверки и результат

- B15 фиксирует API/UX-контракт, разумные лимиты и контрольные fixtures; значения и названия из плана — основа, а не повод спрашивать разрешение на обычные детали реализации.
- Проверять чистые функции, shared funds, Decimal/cents, unknown, невмешательство в рабочее состояние, revisions/409, детерминизм, auth/CSRF и действующие обязательные маршруты. На изменение — подходящие unit/integration checks; перед commits — полный проектный check и whitespace check.
- В B21 пройти L01–L13 через нужные тесты и реальный доступный browser tool. Минимум широкий/узкий экран, клавиатура, zoom 200%, reduced motion; API не заменяет UI evidence. Сохранять версии, реальные команды, результаты, скриншоты и ограничения в task-owned `artifacts/acceptance/decision-lab/`.
- Обычную нехватку runtime/браузера/локальных зависимостей устранять в разрешённом task-owned scope. Не менять ACL, не подменять данные и не обходить согласие или credentials. При реальном внешнем blocker записать `failed/not_run`, источник и следующий допустимый шаг. Заблокированная задача удерживает резерв; таймер не доказывает остановку worker.
- В B22 обновить точный package allowlist, экспорт OpenAPI, подготовить новый ZIP с отдельным именем и checksum. Не перезаписывать прежний candidate. Проверить запуск из распакованного ZIP с чистым browser profile и отдельными task-owned data/портом; не брать assets из кеша checkout. Сохранить действующие ограничения распространения секретов, шрифта, фото и исходных материалов.
- Все B15–B22 и L01–L14 входят в итоговый результат. Если часть не принята, назвать её незавершённой. Итог содержит accepted IDs, commits, worker/reviewer IDs, evidence, путь/checksum нового ZIP и ограничения. Публичная доступность и передача не входят в команду и не подразумеваются.

Если сеанс завершился, повтор той же команды заново сверяет актуальное состояние и продолжает существующие задачи. Нельзя обещать продолжение в фоне без отдельной автоматизации.
