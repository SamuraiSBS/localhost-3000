# Расчётный движок rules-v1

Движок находится в `app/domain/` и состоит из трёх частей: `context.py` строит
контекст клиента и распределяет средства, `features.py` вычисляет признаки из
этих фактов, `scoring.py` агрегирует вклад, уровень риска, денежную оценку и
причины. `money.py` содержит общие точные операции с евроцентами. Модули не
читают БД, не меняют исходные DTO и не выполняют списаний.

## Вход и воспроизводимость

`score_customer(account, services, *, as_of, settings, registry)` принимает
валидированные `AccountSource` / `ServiceSource` из `app/contracts.py`.
В тестах передаётся фиксированный `as_of`; в runtime его можно не передавать,
тогда UTC-часы читаются один раз в начале контекста. Наивные даты отклоняются,
а aware дата нормализуется в UTC. Версия модели — `rules-v1`; результаты не
объявляются вероятностями оттока.

Транзакции не являются входом модели. Отсутствие истории не повышает риск;
`performed` и `not_performed` не меняют баланс, не подтверждают будущую оплату и
не создают историю смены статусов. Новые признаки могут использовать транзакции
только после отдельного, явно проверяемого правила.

## Контекст клиента и корзина

Для одного клиента:

```text
spendable = balance + bonusBalance, если bonusState == unlocked
spendable = balance, иначе
```

`withdrawBalance` не доступен для списания услуги, а `totalReplenished` остаётся
показателем внесённых средств за всё время. До расчёта сумма доступных средств
проверяется на допустимый диапазон евроцентов.

Оцениваемые статусы: `active`, `suspended`, `prolong_wait`. Suspended продолжает
участвовать в прогнозе; prolong_wait участвует и даёт отдельный признак. `blocked`
и `deleted` получают причину исключения и не получают риск продления. Для
оцениваемых услуг `expiresAt <= as_of + H` входит в корзину включительно.
Просроченная услуга также входит как ближайшее возможное продление, но модель не
создаёт пропущенные периоды.

Доступные средства один раз расходуются в порядке `(expiresAt ASC, id ASC)`:

```text
covered = min(price, remaining_spendable)
gap = price - covered
remaining_spendable -= covered
```

Цены и нехватка агрегируются с проверкой переполнения. Цена 0 даёт покрытие 0,
нехватку 0 и не вызывает деление на ноль. Это аналитический порядок распределения,
не утверждение о фактическом порядке биллинга.

`prolong_wait`, просроченный более чем на пять суток, и `active`, просроченный
более чем на пять суток, получают предупреждение качества. Статус источника не
меняется. Снимок с `active`, который давно истёк, остаётся валидным входом с
предупреждением.

## Признаки и score

Registry хранит стабильные `id`, `version`, подпись, описание, default weight,
обязательные поля и evaluator для каждого признака. Каждый evaluator возвращает
значение `0..1`, `available`, объяснение и использованные значения. Встроенные
признаки rules-v1:

| ID | Значение в горизонте | Вес |
|---|---|---:|
| `renewal_proximity` | `clamp(1 - max(expiresAt - as_of, 0) / H, 0, 1)` | 20 |
| `manual_renewal` | 1, когда `autoProlong=false`; иначе 0 | 25 |
| `funding_gap` | `gap / price`; при `price=0` значение 0 | 35 |
| `payment_wait` | 1, когда статус `prolong_wait`; иначе 0 | 20 |

За пределами горизонта все четыре признака равны 0, поэтому услуга измерена как
low/0, а не unknown. Вес каждого признака — Decimal от 0 до 100. Вклад равен
`weight * value`; сумма весов может превышать 100. Все веса 0 запрещены.

```text
raw_score = sum(feature.contribution)
score = ROUND_HALF_UP(clamp(raw_score, 0, 100), 2)
level = low     if score < medium_threshold
        medium  if medium_threshold <= score < high_threshold
        high    if score >= high_threshold
```

Порог по умолчанию: medium 35, high 65. `raw_score` и `score_clamped` сохраняют
смысл ограничения. Для клиента берётся максимальный измеренный score услуги;
при равенстве выбирается услуга с меньшим ID. Подробности и причины этой услуги
включают её признаки в том же порядке, что и модель. Причины с положительным
вкладом сортируются по убыванию вклада, затем по ID; сразу возвращаются три
главные.

Недоступный признак с ненулевым весом не превращается молча в ноль: эта услуга
получает `risk_score=null`, `risk_level=unknown`, `monetary_risk_cents=null` и
список `feature_unavailable`. Другие измеренные услуги клиента остаются
доступными для максимального score. Если у клиента нет оцениваемых услуг или все
они исключены, клиентский score и денежная оценка равны null с причиной unknown.
У оцениваемой услуги вне горизонта score 0 и money 0 — это измеренный результат.

## Денежная оценка

Money хранится как integer евроцентов. Взвешенная стоимость одного продления:

```text
risk_cents = ROUND_HALF_UP(price_cents * score / 100)
```

Score предварительно округлён до двух знаков, затем каждая услуга округляется до
целого цента; после этого суммы услуг складываются. Используется `Decimal` и
`ROUND_HALF_UP`, не float. Каждое входное значение и каждый денежный итог должны
лежать в `0..2^53-1`; превышение вызывает `ValueError` до публикации результата.
`risk_money_cents` проверяет одну услугу, `checked_cents_sum` — агрегат.

Показатель — «стоимость продлений под риском» в выбранном горизонте, а не
подтверждённая вероятность ухода, ожидаемый cash flow или MRR. Если хотя бы одно
из-за отсутствующего взвешенного признака будущее продление нельзя оценить,
полная денежная сумма клиента unknown, а не неполная заниженная сумма.

## Добавление признака

Создайте `FeatureDefinition` с уникальным ID, версией, описанием, полями,
default weight и чистой evaluator-функцией; добавьте его к неизменяемому
`FeatureRegistry` через `with_feature()`. Registry экспортирует metadata для
настроек и передаёт те же evaluator-результаты в score и explanations. Переданные
`weight_overrides` переопределяют соответствующие веса; неизвестный ID, float,
отрицательный вес, вес выше 100 и конфигурация из одних нулей отклоняются.

Чтобы новый ID редактировался также через HTTP settings, контрактный allowlist
в `app/contracts.py` должен быть расширен отдельным интеграционным изменением;
domain registry уже не требует менять формулу или копировать объяснения в API/UI.
Отсутствующие обязательные факты следует возвращать как `available=false` с
причиной, а не подставлять ноль. Для нового правила добавьте ручные тестовые
эталоны независимо от вывода evaluator.

## Ограничения

Пороги, веса, 30-дневный горизонт и формулы — прозрачные правила команды для
первой версии. Источник не содержит датированных исходов, истории удаления или
меток оттока; поэтому обучение, точность, калибровка и экономический эффект не
измерялись. Перемена `as_of` меняет результат по одному исходному снимку, не
создавая новых бизнес-событий.
