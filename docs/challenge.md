## Предмет задачи

Нужно разработать аналитическую веб-систему для маркетолога, который выбирает, каким клиентам биллинговой платформы требуется внимание. Она отвечает на три вопроса: кто может не продлить или прекратить услуги, почему возникает риск и какую сумму бизнес рискует потерять. Уровень кейса — middle (PDF, с. 1).

Пользовательский результат — объяснимый рейтинг для приоритизации работы с клиентами. Численный score сам по себе не доказывает статистически откалиброванную вероятность оттока. ТЗ позволяет команде выбрать формулу, пороги, признаки, периодичность и способ денежной оценки, затем объяснить выбор жюри (с. 2, 13).

## Основной сценарий защиты

1. Жюри запускает решение по README через Docker Compose и входит по логину/паролю.
2. Маркетолог находит клиента под риском в рейтинге, сортируя и фильтруя список.
3. Открывает подробную оценку: score, уровень, услуги, признаки, понятные причины и денежный смысл.
4. Меняет коэффициент через панель или загружает новый снимок данных через обязательный API.
5. Score, рейтинг и денежные показатели обновляются автоматически без ручного reload; метрики отражают ту же версию результата.
6. После перезапуска отредактированные коэффициенты остаются сохранёнными.

Шаги 2–5 непосредственно следуют из демонстрационного задания (с. 12); запуск, доступ и сохранение дополняют его обязательными условиями (с. 6–11). Это план проверки, а не отчёт о выполненной демонстрации.

## Входные данные и ограничения достоверности

- DTO — аккаунты, услуги, транзакции. Решение должно использовать предоставленный набор, который можно расширить для наглядности (с. 2, 8). Расширение следует хранить отдельно и обозначать как демонстрационное.
- Все денежные величины тестовых данных — еврокопейки, 100 единиц = €1 (с. 4). Основной, бонусный и доступный к выводу балансы имеют разные значения; `bonusState` разрешает расход бонусов.
- `autoprolong` допускает автоматическое списание с основного и доступного бонусного баланса; `withdrawBalance` не объявлен автоматически расходуемым (с. 4–5).
- `suspended` не означает прекращение начислений. `blocked` означает невозможность дальнейшего использования/продления. `prolong_wait` длится 5 дней после истечения `expiresAt` и затем переходит в `deleted`; причина `deleted` может быть неуплатой или инициативой клиента (с. 3).
- В исходном снимке нет истории смены статусов и дат удаления (с. 2). По нему нельзя восстановить фактический исторический отток или считать `expiresAt` датой удаления. Накопленная после запуска история и расширенные демонстрационные события требуют отдельного обозначения.
- Реальный источник предполагается обновляющим данные произвольным способом; конкретный брокер/протокол не задан. Обязательный путь приёма снимка — `PUT /api/v1/source/snapshot` (с. 2, 11).

## Дополнительная оценка

ТЗ отдельно называет рабочий OIDC, график количества услуг под риском / предполагаемых непродлений / исторических удалений с различением факта и прогноза и проработанный UX/UI (с. 13). Баллы и веса не указаны. Эти пункты выполняются после обязательного сценария; OIDC не заменяет обязательную базовую аутентификацию по логину/паролю без уточнения организаторов.
