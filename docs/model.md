# Модель риска и денежная оценка

Статус: **предложенная модель для реализации**, версия `rules-v1`. Код расчёта пока не написан и качество прогноза не измерено. Основание задачи: ТЗ, с. 1–8, 12–13; свойства исходных данных — [аудит](data-audit.md). Формула, веса, горизонт и пороги ниже выбраны командой для MVP, а не предписаны организатором.

## Что именно оцениваем

Вопрос модели: есть ли у клиента признаки риска **ближайшего продления хотя бы одной услуги** в горизонте H? Это операционный индекс внимания маркетолога, не обученная вероятность полного ухода аккаунта. В предоставленном наборе нет меток исхода, истории статусов и дат удалений; нельзя обещать accuracy, ROC-AUC, калибровку вероятностей или доказанный экономический эффект.

Минимальная единица расчёта — услуга. Клиент получает максимальный score своих оцениваемых услуг; подробности показывают, какая услуга дала этот максимум. Денежная оценка складывается по услугам, а не умножает все деньги клиента на его максимальный score.

По умолчанию H = 30 суток, UTC. Это **одно ближайшее продление каждой услуги**, попадающее в горизонт, а не все повторные списания за 30 суток. У почасовой услуги цена относится к одному часу; у годовой — к одному году. Поэтому показатель нельзя называть MRR, прогнозом всех продаж за месяц или полной стоимостью клиента.

## Семантика исходных данных

| Поле / состояние | Использование в модели |
|---|---|
| `active`, `suspended` | Услуга может приносить деньги и продлеваться. `suspended` не означает остановку оплаты |
| `prolong_wait` | Есть неоплаченное продление, отдельный сильный сигнал. По ТЗ ожидание длится 5 дней |
| `blocked` | Продлить невозможно: исключить из будущих продлений, показать причину исключения |
| `deleted` | Уже удалена в текущем снимке: исключить из прогноза. Дата удаления неизвестна |
| `balance` | Основные средства, которые могут покрыть продление |
| `bonusBalance` | Добавить к доступным средствам только при `bonusState=unlocked` |
| `withdrawBalance` | Не считать автоматически доступным для списания: для перевода на баланс нужно отдельное действие, которого в DTO нет |
| `totalReplenished` | Показатель ценности клиента и обязательная сортировка; не прибавлять к текущему балансу или потерям |
| `price` | Цена одного периода услуги в евроцентах |
| `transactions` | Контекст объяснения. В v1 не восстанавливать из них баланс, факт оттока или неоплату конкретного продления |

`prolong_wait`, который старше пяти суток, и `active` с давно истёкшим `expiresAt` показывать как предупреждение о качестве данных. Анализатор не переводит статусы, не удаляет услуги и не выполняет списания. Нелогичный, но структурно валидный снимок не становится достоверным от повторной загрузки.

## Доступные средства и общая корзина

Для аккаунта c:

```text
spendable(c) = balance(c) + (bonusBalance(c), если bonusState=unlocked; иначе 0)
due(c) = услуги active/suspended/prolong_wait с expiresAt <= as_of + H
```

Просроченные возобновляемые услуги включаются в ближайшую корзину с отметкой «просрочено». Никаких автоматических попыток восполнить неизвестные пропущенные периоды.

Распределить `spendable` один раз по корзине в порядке `(expiresAt ASC, id ASC)`; для каждой услуги:

```text
covered(s) = min(price(s), remaining_spendable)
gap(s) = price(s) - covered(s)
remaining_spendable -= covered(s)
```

Так баланс 1 000 центов не покрывает одновременно две услуги по 1 000. Это правило аналитического распределения, не обещание реального порядка биллинга. В карточке показать цены корзины, доступные средства и суммарную нехватку. Для `price=0` нехватка и денежный риск равны нулю, деления на ноль нет.

## Признаки v1

Признаки дают значения 0..1. Для услуг вне горизонта признаки v1 равны нулю: нет наблюдаемого риска ближайшего продления в выбранном окне. Услуга при этом остаётся оцениваемой, а не превращается в «нет данных».

| ID признака | Значение внутри горизонта | Вес по умолчанию, баллы |
|---|---|---:|
| `renewal_proximity` | `clamp(1 - max(expiresAt - as_of, 0) / H, 0, 1)` | 20 |
| `manual_renewal` | 1, если `autoProlong=false`, иначе 0 | 25 |
| `funding_gap` | `gap / price`; при нулевой цене 0 | 35 |
| `payment_wait` | 1 при `status=prolong_wait`, иначе 0 | 20 |

Дата на верхней границе горизонта включается в корзину. `renewal_proximity` на ней равен нулю, другие признаки могут быть ненулевыми. Везде использовать одну фиксированную `as_of` на вычисление.

```text
contribution_i(s) = weight_i * feature_i(s)
raw_score(s) = sum(contribution_i(s))
score(s) = round_half_up(clamp(raw_score(s), 0, 100), 2)
score(c) = max(score(s) для оцениваемых услуг c)
```

Веса — баллы влияния, их сумма не обязана быть 100. Увеличение веса не уменьшает риск; если сумма превысила 100, результат ограничивается 100. Показывать исходную сумму и ограничение, чтобы объяснения совпадали с итогом. Все веса 0 запрещены как неработающая модель. Ограничение каждого веса 0..100 — наше решение для понятного редактора, а не требование PDF.

Пороги по умолчанию: `low < 35`, `35 <= medium < 65`, `high >= 65`. Настраиваются вместе с H и весами. Валидация: `1 <= H <= 90`, `0 < medium_threshold < high_threshold <= 100`, минимум один ненулевой вес; изменения атомарны. Интервал H и пороги — документированные настройки команды.

### Когда оценки нет

У клиента без услуг или только с `blocked/deleted`: `risk_score=null`, `risk_level=unknown`, `monetary_risk_cents=null`, понятная причина. Ноль означает измеренный нулевой риск в горизонте, а не отсутствие данных. Пустая история транзакций сама по себе не делает клиента неизвестным, потому что четыре признака v1 используют другие поля.

Структурно испорченный вход отклоняется целиком до замены снимка. Если будущий признак не может вычислиться, возвращать `unavailable` и объяснение. Отсутствие обязательного базового признака делает услугу неоцениваемой; отсутствие дополнительного признака не должно незаметно подставлять ноль. Для v1 структурная валидация обеспечивает наличие базовых полей.

## Денежный показатель

Название в интерфейсе: **«Стоимость продлений под риском»**, валюта EUR. Рядом — горизонт и подпись «одно ближайшее продление каждой услуги; взвешено индексом риска».

```text
score_basis_points(s) = integer(score(s) * 100)    # 0..10000
risk_cents(s) = round_half_up(price(s) * score_basis_points(s) / 10000)
monetary_risk_cents(c) = sum(risk_cents(s) для due(c))
monetary_risk_cents(total) = sum(известных клиентских сумм)
```

Цены и балансы — целые евроценты. Для коэффициентов, долей и округления использовать `Decimal`, не двоичные float; округлять сумму каждой услуги до целого цента и затем складывать. Форматировать EUR только на границе UI. API и Prometheus явно называют единицы. Входные и все вычисленные денежные integers ограничены `0..2^53-1`, включая суммы: иначе JSON/JavaScript и Prometheus binary64 потеряют точность. Превышение отклоняется до записи, прежняя версия остаётся активной; предел выбран командой, не PDF.

Баланс влияет через `funding_gap` с однократным распределением на корзину; поэтому денежная оценка учитывает и стоимость, и средства клиента, и риск. **Не складывать** `balance`, `withdrawBalance`, `bonusBalance` или `totalReplenished` с потерянной выручкой: это разные экономические величины.

Показатель — сценарная оценка стоимости услуг под риском, **не математическое ожидание потерь с подтверждённой вероятностью** и не прогноз будущих пополнений живыми деньгами. Оплата бонусами и заранее внесённый баланс дополнительно отличают его от cash flow. В сводке отдельно показывать валовую цену ближайших продлений, нехватку средств и число неизвестных клиентов. Если все клиенты неизвестны, известная подытоженная сумма технически 0, но UI пишет «Нет денежной оценки», а не «Потерь нет».

## Объяснения и расширение

Каждый признак реализует контракт:

```text
id, version, title, description, default_weight, required_fields
evaluate(service, account_context, as_of, horizon) ->
    value: Decimal | null
    available: bool
    explanation: human-readable text
    evidence: field values / dates / amounts
```

Registry собирает список признаков, модель и настройки используют его метаданные. Новая реализация, запись registry и один набор тестовых примеров должны добавлять признак без редактирования большого `if/else` в API или UI. UI получает метаданные с настройками; неизвестный сохранённый ID не исчезает молча, а требует миграции/явной ошибки.

В карточке причины отсортированы по вкладу, максимум три главные раскрыты сразу, остальные доступны списком. Пример: «Не хватает €10,00 для ближайшего продления», факты `price=1000`, `covered=0`, вклад 35 баллов. Указаны `model_version`, `data_revision`, `settings_revision`, `evaluated_at`; это полезные сведения о расчёте, не декоративная телеметрия.

## Проверочные примеры

Во всех строках одна услуга по 1 000 евроцентов, срок наступил точно в `as_of`, H=30; если не указано иное, `active`, bonus=0. Это **новые ручные контрольные случаи**, а не утверждение о записях исходного файла.

| Случай | Условия | Score / уровень | Денежный риск, cents |
|---|---|---|---:|
| M01 | Баланс 1000, auto=true | 20 / low | 200 |
| M02 | Баланс 1000, auto=false | 45 / medium | 450 |
| M03 | Баланс 0, auto=false | 80 / high | 800 |
| M04 | Баланс 0, auto=true, prolong_wait | 75 / high | 750 |
| M05 | Как M02, вес manual_renewal=50 | 70 / high | 700 |
| M06 | Баланс 0, bonus=1000 locked, auto=true | 55 / medium | 550 |
| M07 | Как M06, bonus unlocked | 20 / low | 200 |
| M08 | Как M03, withdrawBalance=1000 | 80 / high | 800 |
| M09 | Нет услуг или только blocked/deleted | null / unknown | null |
| M10 | Две услуги M02, баланс общий 1000; id первой меньше | 45 и 80; клиент 80 / high | 450 + 800 = 1250 |
| M11 | active, auto=false, баланс 500, expiresAt=as_of+15 суток | 52.50 / medium | 525 |
| M12 | active, expiresAt=as_of+31 сутки | 0 / low; вне горизонта | 0 |

Дополнительно: границы 34.99/35/64.99/65, price=0, одинаковые сроки/порядок ID, clamp при сумме >100, невозможные настройки, rollover календарных периодов для будущего расширения. В v1 периоды не нормализуют цену и не генерируют новые платежи.

## Что улучшать после MVP

Сначала подтвердить формулу и бизнес-смысл с ментором. Затем, если появятся датированные исходы: определить целевое событие и окно, собрать исторические признаки без утечки будущего, сделать временной holdout и baseline, оценить калибровку и стоимость ошибок. Только после этого обсуждать обучение, SHAP, сегментацию и истинное expected loss. Это P2, не скрытая обязательная работа хакатона.
