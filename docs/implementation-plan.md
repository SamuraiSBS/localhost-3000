## Цель MVP

Один маркетолог входит, находит клиента под риском, видит объяснение и стоимость ближайших продлений, меняет коэффициент и видит пересчёт без reload. Затем новый полный snapshot меняет результат; настройки переживают restart. Точные REST endpoints, Prometheus, Docker и OpenAPI входят в этот же MVP.

Стек: FastAPI/Pydantic/Uvicorn + sqlite3 + pwdlib/Argon2 + prometheus-client; native HTML/CSS/ES modules поверх существующего дизайна. [Архитектура](architecture.md), [модель](model.md), [API](api-contract.md), [UX](ui-plan.md). Точные dependency pins/hashes фиксируются первым воспроизводимым build, не подставляются по памяти.

## Вертикальные контрольные точки

**V1: данные → расчёт → защищённый API.** B01–B05: один исходный snapshot, воспроизводимый клиент, объяснение/деньги и настоящий вход. Разрешается временная утилитарная страница для проверки, но не объявлять её конечным UI.

**V2: полный путь в браузере.** B06–B07: тот же клиент находится/объясняется, вес меняет score, другая вкладка обновляется. Seed-данные и новые демонстрационные примеры различимы.

**V3: поставляемое приложение.** B08–B11: metrics/docs/Compose/restart/README/чистый запуск/браузерные доказательства. До V3 не брать ни OIDC, ни chart polish, ни новые сервисы.

## Параллельная работа Codex

После общего B01 области domain engine, storage/auth/API и frontend могут готовиться независимо только при закрытых зависимостях и бронировании непересекающихся точных scopes/resources. По короткой команде оркестратор ведёт один claim за раз; параллельные запуски используют общий ledger. UI mocks нужны только разработке и явно заменяются реальным API перед V2. Не называть mocked screen приёмкой.

Координатор согласует contracts, shared evaluation/repository границы, Docker/CI и интеграцию; правки выполняет выделенный worker в забронированном scope, результат проверяет другой reviewer. File ownership — [agent-workflow](agent-workflow.md), переходы — [CLI](coordination/cli-reference.md). Агентам нельзя одновременно редактировать один контракт. Каждый отдаёт проверяемый diff и свои ограничения.

## Планирование времени

Публичная программа сообщает 48 часов, но точный cutoff сдачи неизвестен. Отсчитывать от **фактического оставшегося времени**, а не считать, что ещё есть 48 часов. До ответа Q-004 этапы относительные.

- Первый рабочий отрезок: B00/B01, затем V1 как можно раньше. Если V1 не проходит, остановить расширение scope.
- Средний отрезок: V2 и B08/B09; постоянно запускать обязательные проверки, не откладывать auth/метрики на последнюю ночь.
- Последние 20–25% времени зарезервировать под B10/B11, исправления и подготовку сдачи.
- B12/B13 допускаются только после зелёного P0 и при сохранённом резерве. При цейтноте убрать обе; типовое «ещё один сервис для бонуса» не должно ломать запуск.

## Готовность задачи и управление изменениями

У каждого принятого Bxx: изменённые пути, команды/результаты, revision, входные snapshot/settings, ограничения, следующий шаг. Runtime `accepted` — только после независимого GO текущей версии и штатного Accept. Наличие документа/заготовки/HTTP200 не заменяет приёмку. Статусы backlog не обновляются рабочими агентами; ledger хранит попытки/историю отдельно. Изменение связанных contract документов требует явного Rebase и нового review.

Перед коммитом `python scripts/check.py` и `git diff --check`, плюс актуальные product tests. Если probe заменяется, check/smoke нельзя оставить тестирующими только probe. Не коммитить исходные фото, чужие изменения, `.env`, логи и весь `artifacts/` автоматически. Сборка, локальный Docker, CI, VPS, HTTPS и публичный E2E — отдельные evidence строки.

Текущее инфраструктурное состояние брать из [infrastructure](infrastructure.md), а не из старого пункта «VPS ещё нет»: документ уже содержит историю Timeweb probe deployment. В рамках планирования live VPS/DNS/CI не проверялись и не менялись. Публичное размещение продукта не заменяет обязательный воспроизводимый запуск по Compose и требует отдельного контекста выпуска.
